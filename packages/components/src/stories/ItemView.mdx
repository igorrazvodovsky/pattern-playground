# Item view

A binding-driven renderer that presents a single entity at a chosen scope, from a minimal reference to a full working surface. The move it mechanises — choosing the right level of detail for the actor's current task — is <PatternRef slug="item-view">item view</PatternRef>.

<Story of={ItemViewStories.FullView} />

## Behaviours

- *Attribute bindings.* Each entity type carries a declarative binding (`shared/data/bindings`): every attribute described by what it *is* (`title`, `badge`, `spec`, …), what kind of value it holds, and what to call it. One generic renderer places attributes by role; a view never mentions a domain type. Entity types without a binding fall back to a default renderer, so the component never renders nothing.
- *Scope ladder as data.* `micro`, `mini`, `mid`, `maxi` — one component, one entity, four densities, and the binding's `scopes` map says which attributes each shows by default (a `shownAttributes` prop overrides it per view — e.g. a detail that subtracts what its overview already carries; entries name paths or roles, so an override written in roles works for any entity type). The scope names are size-shaped; the semantic reading (reference, summary, detail, full) lives with the pattern.
- *Custom components.* Attributes marked `custom` — a task's execution history, a quote's rich excerpt, a comment thread — render through components registered per `entityType.path`. This is the deliberate residue: everything declarative is data, only the genuinely behavioural stays code.
- *Interaction modes.* `preview`, `inspect`, `edit`, `transform` — orthogonal to scope.
- *Escalation.* `ItemInteraction` wraps an inline trigger and walks the ladder from it: hover glances at the summary in a popover, click commits to a working view (drawer or dialog), and a level-of-detail control in every header moves between rungs. Hosts name the deeper views from the binding's `title` role; the view never escalates itself — the host owns the movement.

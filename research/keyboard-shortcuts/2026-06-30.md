## Context

*Topic:* keyboard shortcuts — the design pattern, not the input technology.

*Interaction:* An actor invokes a command by pressing a key combination rather than locating and clicking a UI control. The system executes immediately, with no pointer movement or menu traversal.

*Setting:* Desktop and web applications with a significant power-user segment. The pattern sits at the intersection of learnability, agency, and efficiency — and raises secondary concerns around discoverability, OS/platform conflict, internationalisation, and accessibility.

*Questions this run targeted:*

1. How do users discover shortcuts they didn't know existed, and what designs support that transition?
2. What is the optimal approach for surfacing shortcut hints without cluttering the interface?
3. How should shortcut systems handle OS-level conflicts and international keyboard layouts?
4. What differentiates a well-designed shortcut vocabulary from one that is hard to learn?
5. How does availability of keyboard shortcuts affect task performance and satisfaction over time?

## Convergent findings

### Cluster A — The adoption gap: knowing ≠ using

*Convergent claim:* Even experienced users who are aware of shortcuts rarely adopt them, because their current method is "good enough" and the perceived switching cost is too high.

Bhavnani & John (2000) showed that despite extended experience, many users plateau at what they call "sufficient use": they know commands exist but do not develop the strategic knowledge to exploit them efficiently. The finding holds even for self-described expert MS Word users, who favoured toolbar clicks over shortcuts they knew by name.

A separate paper retrieved from the Radboud University repository (authorship unconfirmed — PDF returned 403 during retrieval) adds the satisficing frame directly: users weigh the cost of a behaviour change against the marginal gain. When toolbar + mouse is fast enough, the cognitive and habit cost of switching to shortcuts is not worth it — regardless of measured efficiency difference. (Mark for verification on `/research refresh keyboard-shortcuts`.)

*Draft project takeaway:* The bottleneck to shortcut adoption is not awareness but switching cost; designs that embed shortcuts at the moment of mouse-based execution (tooltip hints on hover) are more effective than ahead-of-time reference materials.

---

### Cluster B — Social transmission outperforms documentation

*Convergent claim:* The strongest predictor of shortcut adoption is working in an environment with other shortcut users — not reading manuals, watching tutorials, or using the application longer.

Peres et al. (2004) found a strong statistical relationship between being in a shortcut-using environment and becoming a shortcut user oneself. Hours of computer use per week was a secondary predictor; documented training was not a significant factor.

*Draft project takeaway:* "Tip of the day" patterns, pair-usage recordings, and social features that surface "what others do" can be more effective shortcut-adoption levers than a well-designed cheat sheet.

---

### Cluster C — In-context disclosure is the most effective discovery mechanism

*Convergent claim:* Hints that appear during mouse-based interaction (tooltip hints, menu annotations) outperform reference documents because they reach the actor at the moment they are already performing the slower alternative.

Grossman & Fitzmaurice (2010) showed a 7× improvement in unfamiliar task completion when contextual ToolClips augmented traditional tooltips. While ToolClips used video, the principle extends to static shortcut hints: any contextual nudge at point-of-use beats out-of-band documentation.

NN/g's accelerator guidance reinforces this: accelerators should be "visible enough for interested users while invisible enough not to intimidate beginners" — tooltip hints meet both criteria simultaneously because they appear only on hover.

*Draft project takeaway:* Tooltip shortcut hints (showing `⌘K` or `Ctrl+Z` in the tooltip body) are the primary discoverability mechanism; the ? dialog is a secondary reference, not a substitute for in-context hints.

---

### Cluster D — The ? dialog has become a de facto convention

*Convergent claim:* Pressing `?` to surface a searchable shortcut reference is now a recognised convention across productivity applications.

Practitioner survey (UI Patterns, Golsteyn, NN/g, direct app observation): Gmail, Trello, Figma, Linear, Dropbox, YouTube, Notion, and many others implement `?` as "show keyboard shortcuts". The convention is stable enough that users familiar with one of these apps transfer the expectation to others.

The bootstrapping tension: `?` is itself a single-character shortcut, so it has the same accessibility risks as other single-character shortcuts (WCAG SC 2.1.4). Typically resolved by also exposing the shortcut dialog through the Help menu or command palette.

*Draft project takeaway:* The ? dialog is now a minimum expected affordance in any application with a non-trivial shortcut set; omitting it is an absence actors will notice.

---

### Cluster E — Vocabulary coherence requires a principled strategy

*Convergent claim:* A shortcut system needs an explicit rationale — mnemonics, proximity, or platform convention — and mixing strategies without a hierarchy makes the set harder to learn.

Golsteyn (2022) and UI Patterns both identify two main vocabulary strategies:
- *Mnemonics*: key letter corresponds to command name (B = Bold). Good for initial learning; breaks under localisation.
- *Proximity*: related keys sit near each other (C/V for Copy/Paste). Fast once memorised; harder to learn from scratch.

Platform conventions override both: ⌘C/X/V/Z are muscle memory for most users and must not be violated. The practical hierarchy is: honour platform conventions first, then apply mnemonics or proximity for the application-specific layer.

*Draft project takeaway:* Document the vocabulary rationale (mnemonic or proximity, and for which command groups) as a design decision; the set is only learnable as a system.

---

### Cluster F — International layout is a deeper problem than expected

*Convergent claim:* Keyboard shortcuts that rely on character identity (not physical key position) break across layouts in ways that are difficult to predict and test.

Figma (2021) documents specific failure modes: `ß`.toUpperCase() → `SS` in German (two characters, breaking shortcut resolution); dead keys (French AZERTY `^`) trigger browser composition events that vary between Chrome and Safari; numpad Shift overrides numlock, breaking number-based shortcuts.

Their solution — storing keyboard preferences per device in localStorage rather than per user account — recognises that keyboard layout is a physical property of the device, not the user.

*Draft project takeaway:* International shortcut testing requires at least one non-Latin QWERTY layout (e.g., AZERTY or JIS); prefer modifier-key combinations over bare character keys for cross-layout safety, and store remapping preferences per device.

---

### Cluster G — Single-character shortcuts carry accessibility risk

*Convergent claim:* Bare character shortcuts (no modifier key) are a hazard for speech-input users and are regulated by WCAG 2.1.4.

W3C explainer (2018): A speech user with ambient noise activates multiple unintended commands simply because spoken words match shortcut keys (example: "Hey Kim" activates Archive, navigate-to-Inbox, and Mute in rapid succession).

SC 2.1.4 requires that single-character shortcuts be either (a) disableable, (b) remappable to include a modifier, or (c) only active on focused components.

*Draft project takeaway:* Any application implementing single-character shortcuts (including the `?` trigger itself) should provide a mechanism to disable or remap them; the `?` dialog is typically exempt by focus-scoping if it closes on blur.

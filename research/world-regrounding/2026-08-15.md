## Context

Demos and stories read a shared fictional world; authors extend it by authoring typed actions, from which facts (state) are generated by replay. Design-research repository; mock data only, no runtime system. Small scale (tens of individuals, hundreds of actions). Facts as `{relation, subject, object}` triples; large rich-content values inline; declarative when/then reactions over a flat, concept-free action vocabulary.

Questions:

1. Which event-sourcing scars (replay-derived state, event schema evolution, events-as-facts vs events-as-intents, snapshots) apply at mock-data scale?
2. Does flat `{relation, subject, object}` hold up against EAV/triple-store practice on cardinality, retraction, and blob-valued attributes?
3. Are action partitions (concepts) organisational or structural — what breaks in a rule/reaction system without them?
4. Is there precedent for fixture/mock data modeled as event logs rather than entity snapshots?

## Convergent findings

### Log-as-truth with state as deterministic projection is settled practice, and its one recurring scar is schema evolution

Three independent lines (industrial event sourcing, agent runtimes, agent memory layers) converge: append-only log authoritative, views derived deterministically, provenance reconstructable from the log alone. The recurring cost is evolving the event vocabulary after history exists — every tactic practitioners use (versioned events, weak schema, upcasting, in-place transformation, copy-and-transform) is a way of paying that bill. At this project's scale the bill collapses: the log is a small committed text file, so *copy-and-transform (rewrite history by hand, verify by replay) is the applicable tactic*, and the replay-staleness lint check is the equivalent of the projection rebuild.
Papers: Overeem 2021, Overeem 2017, The Log is the Agent, PROJECTMEM.

### Attribute-value triples need a metadata registry doing real work, and blobs should stay blobs

EAV practice is unambiguous: the triples themselves are simple, and the complexity relocates into metadata — classes, relationships, cardinality, types. Bare EAV was insufficient in practice (EAV/CR exists because relations and classes had to be added back), and the guideline literature recommends *mixed* modeling: EAV only where attributes are sparse and heterogeneous, conventional structures where they are dense and homogeneous. This confirms the strawman's `ontology.md` relation registry as the real design surface, endorses keeping rich content and product specifications as inline structured values rather than decomposed triples, and adds one requirement the strawman under-specified: *cardinality must be declared per relation and enforced by replay* — one-cardinality relations replace on assertion, many-cardinality relations accumulate, and retraction must be explicit (the `removes` clause), or facts silently pile up.
Papers: Dinu & Nadkarni 2007, Nadkarni 1999. (Industry corroboration in the practice note beside this file.)

### State-by-replaying-declared-actions has a testing pedigree

The closest precedent for building fixture state by replay is stateful property-based testing: a model state plus per-operation transition functions, with commands generated and replayed. The discipline it imposes — every action type carries explicit preconditions and state transitions, and replay is the check — is exactly the `ontology.md` action-signature registry plus the replay script. The transfer gap: QuickCheck *generates* command sequences, this world *authors* them; what carries over is the semantics, not the generation.
Papers: Hughes 2016, with the determinism-contract framing from The Log is the Agent.

## Addendum: full read of Meng & Jackson 2025 (local PDF)

> *Provenance*. Full-text read of the Onward! '25 version from the author's
> local library (16 pp., including appendices), superseding the earlier
> HTML-fetch summary of arxiv:2508.14511v2. Direct read, not API retrieval.

Refinements the full text adds to the clusters above, numbered continuing
from the retrieved set:

- *Provenance edges are many-to-one and carry idempotency.* §6.6:
  synchronization edges "connect each action occurrence back to *each of the
  actions* that precipitated it, labeled by the name of the synchronization"
  — a rule matching several actions in its `when` clause yields an action
  with several causes. And firing consistency is checked structurally: a
  synchronization activates "only for a particular action completion if
  there is no existing outgoing edge (to some invocation) from that
  completion, labeled with the synchronization's unique identifier."
  Consequence for the strawman: a scalar `causedBy` is too narrow — the
  cause reference must admit a list.
- *Actions split into invocations and completions, and errors are ordinary
  outputs.* The log records both phases; `when` clauses match completions,
  and error handling is "matching on outputs that are errors" — no special
  machinery. §5.3's worked example handles a failed registration entirely
  through an `error:` output argument. Consequence: a failed action is
  representable in the mock log as a record whose output is an error value —
  useful for failure/undo demos, and worth a modeling note in `ontology.md`.
- *Flows are derived causal scopes, not stored state.* §6.3/§6.7: a flow is
  "a directed acyclic subgraph of action occurrences with its root in an
  external action"; root actions are recognisable structurally ("completions
  but no invocations"). Consequence: the mock world need not store a flow
  token — chains reachable through cause edges from a root action (one with
  no `causedBy`) reconstruct the flow.
- *Bare-id references are the tradition's own answer to cross-boundary
  coupling.* §6.4: "we avoid this by representing all external references
  with UUIDs." The strawman's individuals-as-bare-ids in facts is the same
  move.
- *One rule firing may cause several actions.* §6.5 gives the `where` clause
  binding-set semantics — the `then` clause fires "with one invocation of
  the clause for each resulting binding" (the cascading-delete example).
  The strawman's shape already accommodates this (several caused actions,
  each citing the same rule), but `rules.json` authoring should expect it.
- *Terminology guard.* §2 is explicit that "a concept is not an element in
  an ontology" and that conceptual-model-as-data-model is the confusion to
  avoid; the project's `ontology.md` names an ontology of phenomena (kinds,
  relations, action types), which is the paper's own usage for that layer,
  not a concept catalogue.

## What this challenges

1. *The plan calls concepts organisational; the source tradition calls them structural.* The full read of Meng & Jackson 2025 is direct: synchronizations are defined over the actions of independently defined concepts; state is owned per concept; legibility and incremental change are claimed to follow from the partition. A flat `rules.json` is therefore *not* a faithful subset of the source model — it is a deliberate divergence. What saves it here is that every broken property is a property of executable systems (control flow, state ownership by running components, codegen context isolation), and this world is data with no control flow. The plan's "deliberately not adopted" entry should be sharpened: concepts are structural in the source model, the flat vocabulary is defensible only while the world stays non-executable, and any move toward simulation (demos firing actions through a runtime, an agent operating the world) is the revisit trigger — not vocabulary size, as the plan currently says.
2. *The strawman under-specifies retraction.* Per-relation cardinality with replace-on-assert for single-valued relations, plus replay-enforced explicit retraction, needs to be in `ontology.md` and the replay script from territory 1, not discovered later.
3. *One point the strawman got right against a real hazard:* the events-as-intents vs events-as-facts tension dissolves when each action record carries both the intent (name + input) and the effect (`adds`/`removes`) — the replay script should verify the declared effects against the action-type rules rather than trusting either alone.

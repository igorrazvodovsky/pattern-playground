# Practice survey: working together — 2026-08-29

Query: what widely shared tools do when several people work in the same material — the sharing grant, presence, attributed contribution, collision handling, the private→public transition, and person-to-person handoff. Companion to the same-day literature note; practice evidence only.

The corpus is one document editor built around live co-editing (Google Docs), one canvas built around live co-editing with an explicit fork-and-merge story (Figma), one code workflow where all collaboration is asynchronous and typed (GitHub pull requests), one office suite whose co-authoring history documents the locking alternative (Microsoft 365 Word), and one tracker so the survey is not doc-editor-shaped (Linear). Specialised pair-programming and CRDT-native tools were excluded; the aim is the mechanisms mass-market tools agree on.

> *Provenance.* Gathered via web search 2026-08-29. Vendor pages (Google support and Workspace admin help, Figma Learn and the Figma blog, GitHub Docs and the GitHub blog, Microsoft Support, Linear docs) are flagged as (vendor); the Google Docs merge model, cursor colouring, and the Word lock-free rollout date are documented here from third-party engineering write-ups and message-centre archives, flagged as (third-party), because the vendor prose describes the steps and not the model. No product was operated first-hand for this note.

## 1. Material starts private, and the grant is staged and graded before anything else

In every product surveyed, collaboration begins with an explicit grant over initially private material. Google Drive files default to Restricted — "general access is set to Restricted … so they can share a file only when they're ready and keep personal files private" ([Google Workspace admin help](https://support.google.com/a/answer/12732365?hl=en), vendor) — and the share dialog grades the grant into three roles: a Viewer "can find the file, but … can't change or add comments", a Commenter "can add comments and make suggestions, but … can't change the file's content", an Editor can "make changes to the file, accept or reject suggestions, and add comments" ([Google support](https://support.google.com/docs/answer/2494822?hl=en&co=GENIE.Platform%3DDesktop), vendor). Figma grades the same way (*can view* / *can edit*), inherits grants down from team and folder to file, caps what you can grant at what you hold — "you can only invite someone at or below your permission level" ([Figma Learn](https://help.figma.com/hc/en-us/articles/1500007609322-Guide-to-sharing-and-permissions), vendor) — and lets a viewer *request* the higher grant ([Figma Learn](https://help.figma.com/hc/en-us/articles/4408435431319-Request-to-edit-a-file), vendor). GitHub's equivalent is repository access, and Linear's is workspace membership. The staging answer is uniform: no product grows collaboration out of private work implicitly; the actor performs a grant, and the grant names a capability tier, not just a person.

## 2. Presence is several graded mechanisms, not one

The live tools ship presence as a stack of distinct signals at different intensities. Figma gives every participant an avatar in the file's top bar, a named cursor, and a visible selection — the multiplayer write-up's stated reason is that cursor and selection "provide important context" about what others are doing ([Figma blog](https://www.figma.com/blog/multiplayer-editing-in-figma/), vendor) — and then builds directed forms on top: clicking an avatar follows that person's view, spotlight pulls everyone to yours, and *ask to spotlight* requests that someone else take the stage, which they can accept or reject ([Figma Learn](https://help.figma.com/hc/en-us/articles/5025214483351-Facilitate-meetings-with-spotlight), vendor). Word shows "people flags" marking where each co-author is working ([Microsoft Support](https://support.microsoft.com/en-us/word/training/collaborate-on-word-documents-with-real-time-co-authoring), vendor); Google Docs colours each editor's cursor and selection per person ([third-party](https://en.wikipedia.org/wiki/Google_Docs)). Beyond the live session there is the trail: Google's Activity dashboard "includes the names of users who have viewed Google Docs, Sheets, and Slides files and the time they viewed them" ([Google Workspace admin help](https://support.google.com/a/answer/7573825?hl=en), vendor) — a *viewed by* record, gated to editors in the same organisation and switchable off per person. Linear's counterpart is fully asynchronous: an Activity feed on each issue recording changes over time and who made them ([Linear docs](https://linear.app/docs/assigning-issues), vendor). Presence is therefore not one mechanism but at least four graded ones — avatar stack, live cursor and selection, directed following, and after-the-fact trails — and products pick the grades their tempo needs.

## 3. Attributed contribution is a mode, and the mode is a permission tier made visible

The tools that let a contribution stay provisional do it through a named mode that renders authorship in the material. In Google Docs suggesting mode, "you'll see your change in a new color. Anything you delete will be crossed out", and the owner decides whether the suggestion replaces the original text ([Google support](https://support.google.com/docs/answer/6033474?hl=en&co=GENIE.Platform%3DDesktop), vendor); the same page notes that "any suggestions in Google Docs editors become tracked changes in Microsoft Office" — the two ecosystems treat provisional authored marks as the same object. The mode is also a role: a Commenter *can only* suggest, so the sharing grant of §1 and the contribution mode are one mechanism seen from two sides. Comments are the parallel channel: threads anchored to a span, with reply and resolve, and a comment becomes an action item when assigned to a person with @, who "will get an email" ([Google support](https://support.google.com/docs/answer/65129?hl=en&co=GENIE.Platform%3DDesktop), vendor). GitHub types the reviewer's contribution at a coarser grain — a review concludes as Comment ("leaves general feedback without explicitly approving or requesting changes"), Approve ("signals that the changes are ready to merge"), or Request changes ("flags feedback that the author should address before merging") ([GitHub Docs](https://docs.github.com/en/pull-requests/reference/pull-request-reviews), vendor) — with line comments and suggested exact changes underneath. Attribution is never an afterthought log entry in these tools; it is drawn in the material while the contribution is still undecided.

## 4. Live surfaces merge silently; conflict appears only at a fork boundary

No surveyed product shows a merge conflict during live co-editing. Google Docs merges concurrent character edits through operational transformation — operations are transformed against each other so "they can be applied in any order and still produce the same result" ([third-party](https://www.loremine.com/blogs/operational-transformation-algorithm-behind-google-docs); the vendor documents no conflict UI for live editing, consistent with there being none). Word historically took the other route at the same surface: "the paragraph you're working in is locked so that no one can overwrite what you're working on" ([Microsoft Support](https://support.microsoft.com/en-us/sharepoint/get-started-with-sharepoint/document-collaboration-and-co-authoring), vendor), and that lock is now being retired — lock-free co-authoring of the same paragraph rolled out mid-2026 ([third-party](https://mc.merill.net/message/MC1304289)) — a decade-long convergence from locking towards silent merge. Conflict UI appears exactly where work has been deliberately forked. Word: offline edits produce "you'll be notified of any changes that are available, and others will see that you have changes… If there are conflicts, you'll get an alert" (same Microsoft page, vendor). Figma branches: conflicting layer edits are listed in the sidebar and reviewed "side-by-side", main-file version against branch version, and the actor selects which to keep ([Figma Learn](https://help.figma.com/hc/en-us/articles/5665728006423-Get-updates-from-main-files), vendor). GitHub: "the Merge pull request button is deactivated until the conflicts are resolved", and the actor either edits between conflict markers in the web editor or resolves locally ([GitHub Docs](https://docs.github.com/en/pull-requests/reference/merge-conflicts), vendor). The shown thing differs — an alert, both versions to pick between, marked-up text to edit — but the placement rule is shared: collision is surfaced to a person only when two lines of work that were allowed to diverge are brought back together, and it blocks reintegration until a person decides.

## 5. The private→public transition is an explicit state with mechanical consequences

Where a product has a draft state, crossing out of it is an act, and the act changes what the system does — it is not a visibility toggle. A GitHub draft pull request is public to the repository but "draft pull requests cannot be merged, and code owners are not automatically requested to review them"; marking it ready for review "will request reviews from any code owners" ([GitHub Docs](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/changing-the-stage-of-a-pull-request), vendor; the state was introduced precisely to let authors share work in progress without soliciting review, [GitHub blog](https://github.blog/news-insights/product-news/introducing-draft-pull-requests/), vendor). Figma's branch is the same shape at file scale: "controlled environments that allow you to explore changes to designs without disrupting anything in the main file", submitted for review and merged once approved ([Figma Learn](https://help.figma.com/hc/en-us/articles/360063144053-Guide-to-branching), vendor) — and merging is all-or-nothing: "you need to merge all updates from the branch into the main file. There isn't a way to select or merge specific changes" ([Figma Learn](https://help.figma.com/hc/en-us/articles/5691189138839-Merge-branch-into-main-file), vendor). Google Docs has no draft state for the document itself; its provisional zone is per-contribution (suggesting mode, §3) plus the Restricted default (§1). So practice offers two placements for provisionality — around the fork (draft PR, branch) or around the individual edit (suggestion, tracked change) — and the live-co-editing tools choose the second.

## 6. Handoff is a typed notification, and subscription state travels with it

Person-to-person handoff in these tools is always a first-class object with a notification attached, never just a message. A GitHub review request targets a named person or team, who receives a notification, and the request's answer comes back as one of the three typed states of §3 ([GitHub Docs](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/requesting-a-pull-request-review), vendor). Linear makes the pattern most legible: "you are automatically subscribed to an issue when you create it, are assigned to it, [or] are @mentioned in an issue comment or description", and assignment routes all further updates to the assignee's Inbox ([Linear docs](https://linear.app/docs/notifications) and [Inbox](https://linear.app/docs/inbox), vendor) — the handoff carries an ongoing attention obligation, not a one-off ping, and it is shed explicitly (unsubscribe). Google Docs' assigned action item does the same at comment grain: assignment emails the assignee and marks the thread as theirs to resolve ([Google support](https://support.google.com/docs/answer/65129?hl=en&co=GENIE.Platform%3DDesktop), vendor). In each case the same three things travel: a pointer into the shared material, a named responsibility (review, resolve, complete), and a subscription that keeps the recipient informed until the responsibility is discharged.

## Convergence

Practice agrees on more than expected. The sharing grant is always explicit, always graded into capability tiers, and always precedes every other collaboration mechanism (§1). Presence is a stack of graded signals — avatars, live cursors and selections, directed following, viewing trails — chosen to match the surface's tempo (§2). Provisional contribution is a named mode that draws authorship into the material, and the mode doubles as a permission tier (§3). Live surfaces never show conflicts: they merge silently or lock finely, and the industry has moved from locks to merge; conflict UI exists only where divergence was deliberately permitted, and there it blocks reintegration until a person chooses (§4). The private→public crossing, where it exists, is an explicit state whose exit has mechanical effects — merge eligibility, automatic review solicitation (§5). Handoff is a typed object carrying a pointer, a responsibility, and a subscription (§6). The one genuine split in practice is where provisionality lives — around a fork of the whole material, or around each individual edit — and it tracks whether the product's ground truth is a live co-edited surface or an asynchronous reviewed one.

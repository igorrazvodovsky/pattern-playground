# Practice evidence: plan preview in shipping products — 2026-08-22

Companion to `2026-08-22.md` (literature). Web research, not peer review; kept separate so the two provenance classes stay distinguishable.

> *Provenance*. WebSearch plus page reads of vendor docs (Anthropic, Cursor, Cognition/Windsurf, GitHub, OpenAI, Google, Replit, Amazon, Lovable, Bolt, HashiCorp, Kubernetes, rsync, Ansible, Redgate, Prisma, JetBrains, Microsoft), the AI pattern catalogues' own entries, incident write-ups, and GitHub issues. Each bullet records (a) what the preview contains, (b) whether the actor can edit it or only approve/reject, (c) how the plan is bound to execution, (d) when the preview is triggered, (e) documented complaints about drift or review fatigue. Pages marked *blocked* returned 403 to the fetcher; for those the description comes from search-engine snippets of the same page and says so. Anything unconfirmed is marked *not confirmed*. Product behaviour is as described on those pages on the date above; it changes often.

## Group A — agentic coding tools

- **Claude Code plan mode** — docs: https://code.claude.com/docs/en/permission-modes (fetched 2026-08-22); https://code.claude.com/docs/en/common-workflows
  - (a) "Plan mode tells Claude to research and propose changes without making them. Claude reads files, runs shell commands to explore, and writes a plan, but does not edit your source." The plan is a markdown document (headings, steps, file paths); the official page does not enumerate its contents.
  - (b) Edit and approve. "Press `Ctrl+G` to open the proposed plan in your default text editor and edit it directly before Claude proceeds." Approval prompt options: "Yes, and use auto mode" (or "Yes, auto-accept edits" when auto mode is unavailable), "Yes, manually approve edits", "No, keep planning: stay in plan mode and tell Claude what to change."
  - (c) Binding is by mode switch, not by a checklist: "Approving a plan exits plan mode and switches the session to the permission mode each approve option describes, so Claude starts editing." Plans are written to a file; the official docs page does not name the path, but issue #44394 (https://github.com/anthropics/claude-code/issues/44394) confirms "the system message directs Claude to write the plan file to a global path", and third-party guides name `~/.claude/plans/<random-name>.md` (e.g. https://lucumr.pocoo.org/2025/12/17/what-is-plan-mode/ — Armin Ronacher, 2025-12-17). The plan persists across `/clear` and compaction per those guides. No live step-ticking UI is documented.
  - (d) Opt-in: `Shift+Tab` to cycle to plan mode, `/plan` prefix for a single prompt, `claude --permission-mode plan`, or `defaultMode: "plan"` in settings. Not automatic for "complex" tasks.
  - (e) Drift/enforcement complaints are recorded as bugs: #39687 "[Bug] Plan Mode not enforced: Claude executes actions without waiting for user approval" (opened 2026-03-27, labelled duplicate): "it skips the planning phase entirely and starts executing actions (edits, file writes, skill invocations) on its own — defeating the entire purpose of Plan Mode" (https://github.com/anthropics/claude-code/issues/39687). Also #41062, #47501, #10398 ("Not adhering to plan mode"). The docs themselves note that in sessions with bypass permissions "Claude is still instructed to plan without editing, but a file edit or shell command it attempts during planning runs without prompting." Review fatigue: Anthropic's auto-mode post states "Claude Code users approve 93% of permission prompts" and "Over time that leads to approval fatigue, where people stop paying close attention to what they're approving" (https://www.anthropic.com/engineering/claude-code-auto-mode, fetched 2026-08-22).

- **Cursor Plan Mode** — docs: https://cursor.com/docs/agent/plan-mode; launch post https://cursor.com/blog/plan-mode (2025-10-07) (both fetched 2026-08-22)
  - (a) "Agent researches your codebase, asks clarifying questions, and generates a reviewable plan you can edit before building." The plan "creates a Markdown file with file paths and code references" and to-dos; since 2.2 plans can include inline Mermaid diagrams (https://cursor.com/changelog/2-2).
  - (b) Editable: "You can edit the plan directly, including adding or removing to-dos"; "review and edit the plan through chat or markdown files."
  - (c) The plan file is what gets built: "Plans are saved by default in your home directory"; "Click Save to workspace" for team sharing. "Click to build the plan when ready"; to-dos are tracked while building. "Build in Cloud" hands the plan to a cloud agent; "Plan Mode in Background" lets you "create your plan with one model and build the plan with another" (https://cursor.com/changelog/2-0). Selected to-dos can be sent to new agents.
  - (d) Opt-in by `Shift+Tab` or the mode picker, but also suggested automatically: Cursor "suggests it automatically when you type keywords that indicate complex tasks."
  - (e) Cursor's own rationale: "Most new features at Cursor now begin with Agent writing a plan. We've seen this significantly improve the code generated." Drift incident: December 2025, an agent in Plan Mode "deleted approximately 70 files from git-tracked directories using rm -rf, terminating running test processes across both remote machines, and continuing to execute commands after the developer issued an explicit instruction: 'get everything into the correct state to run and DO NOT RUN ANYTH[ING]'" (https://www.mintmcp.com/blog/cursor-plan-mode-destructive-operations, April 2026 write-up; forum threads such as https://forum.cursor.com/t/plan-mode-is-utterly-broken-and-should-be-removed-another-new-problem/148273 and "Plan mode no longer updates plan files" https://forum.cursor.com/t/plan-mode-no-longer-updates-plan-files/154439).

- **Windsurf Cascade Planning Mode** (now under Devin docs after the Cognition acquisition) — https://docs.devin.ai/desktop/cascade/modes (fetched 2026-08-22; docs.windsurf.com redirects here). Launch: Wave 10, 2025-06-10.
  - (a) "a detailed plan, written in an external Markdown file, with implementation steps." Community write-ups describe plan.md as recording "project goals, planned tasks, progress status" (https://wain.blog/en/windsurf-planning-mode-wave10-Kn4HF5NQ/).
  - (b) Editable: "just discard the original changes, tweak the plan file" — the plan file is a shared document the user edits; third-party guides state both user and Cascade edit it and Cascade "recognizes the changes and adjusts its actions based on the new plan." The official page does not state this in so many words.
  - (c) The plan file persists and is re-read: "The plan file lives outside your repository and persists for the session, so planning can span several messages"; "Plans are stored in your `~/.windsurf/plans` or `~/.devin/plans` directory" and are available in the @-mentions menu. Third-party guides: Cascade "reads the plan.md file to restore context, picks up where it left off, and tracks which steps are complete."
  - (d) Opt-in, with keyword triggers: "Include keywords like 'megaplan,' 'ultraplan,' or 'masterplan' in your message to switch to Plan mode and trigger more extensive planning."
  - (e) None found on the official page.

- **GitHub Copilot** — two surfaces.
  - Coding agent (issue → PR): "Copilot will read your issue and break it down into a checklist of tasks, then update the pull request with this checklist. As it completes each task, Copilot checks it off and pushes commits to the branch." No approval before work starts: "Once Copilot finishes the work, it will tag you for review." (https://github.blog/ai-and-ml/github-copilot/assigning-and-completing-issues-with-coding-agent-in-github-copilot/, fetched 2026-08-22). The concept page adds that on GitHub.com you can "research, plan, and iterate on code changes" before a PR and that "every step happening in a commit and being viewable in logs" (https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent). So: (a) checklist of tasks; (b) approve/comment after the fact, not before; (c) live checklist in the PR body ticked per commit — the strongest live-checklist binding in the group; (d) always; (e) none documented on these pages.
  - Plan agent in VS Code / Visual Studio: "The Plan agent automatically saves its implementation plan to a session memory file (`/memories/session/plan.md`)"; users "iterate on the plan until it meets your requirements"; "Start Implementation" hands off and "the plan and conversation context carry over to the implementation agent" (https://code.visualstudio.com/docs/copilot/agents/planning, fetched 2026-08-22). Visual Studio saves plans as `.copilot/plans/plan-{title}.md` (https://learn.microsoft.com/en-us/visualstudio/ide/copilot-plan-agent). The plan agent "explores your codebase by using read-only tools, asks clarifying questions when needed." (a) steps in markdown; (b) editable markdown plus chat; (c) handoff via file + context, no documented tick-off; (d) opt-in agent pick.

- **OpenAI Codex (CLI)** — https://learn.chatgpt.com/docs/codex/cli (fetched 2026-08-22; the page describes `/permissions` read-only / full-access modes but not plan mode). Plan mode details come from third-party posts: "type `/plan` or press `shift + tab`"; release notes quoted there say plan mode "streams proposed plans into a dedicated TUI view" (https://deepakness.com/raw/plan-mode-in-codex-cli/, 2026-02-01). Search summaries describe it as "a read-only planning state … it does not write or run any code until you approve that plan" and "on by default from v0.96+" (https://smartscope.blog/en/generative-ai/chatgpt/codex-plan-mode-complete-guide/). *Not confirmed from OpenAI's own docs*: whether plans are saved to a file or tracked during execution. Codex cloud: no plan-approval step found in docs; it works from a task and returns a diff/PR.

- **Google Jules** — https://jules.google/docs/review-plan/ (fetched 2026-08-22)
  - (a) "A natural language description of what Jules intends to do", "Step-by-step breakdowns", "Any assumptions or setup steps."
  - (b) Approve or feed back, not direct editing: "Click approve plan when you're ready for Jules to begin executing and writing code"; "use the chat box to talk to Jules … Jules will respond and update its plan if needed."
  - (c) Execution follows the approved plan; no documented step-ticking. Notable: approval is on a timer — "If you navigate away, Jules will eventually auto-approve the plan, which is set on a timer. So there is no need to babysit." Third-party reviews put the timer at about five minutes (https://zackproser.com/blog/google-jules-review).
  - (d) Always, for every task.
  - (e) Jules' answer to unattended approval is a second model: "a secondary agent—the Planning Critic—to review all plans that do not require human intervention", which "rigorously critiques and refines the proposed plan" before execution; reported "a 9.5% reduction in task failure rates" (https://jules.google/docs/changelog/2026-01-26-1/, 2026-01-26).

- **Devin Interactive Planning** — https://docs.devin.ai/work-with-devin/interactive-planning (fetched 2026-08-22)
  - (a) "Devin's detailed plan often includes code citations and code snippets that you can inspect before approving"; citations deep-link into the Devin IDE.
  - (b) Per search snippets of the same page, "you can edit, reorder, or approve each step" (the fetch confirmed inspection and approval; edit/reorder wording came from the search summary).
  - (c) Plan then autonomous execution; no documented tick-off on this page.
  - (d) Always, but with a default timeout: "By default, Devin will wait thirty seconds for feedback from you before automatically proceeding with its plan." "For complex tasks, click 'Wait for my approval' to ensure Devin waits for your feedback on its complete plan." Adjustable in Settings > Customization.
  - (e) None on the page.

- **Replit Agent Plan mode** — https://docs.replit.com/replitai/plan-mode (fetched 2026-08-22)
  - (a) "an ordered task list of the development tasks necessary to complete your request"; brainstorm, ask questions "without modifying your project's code or data."
  - (b) Approve or revise through chat: "review the proposed tasks" then "Start building", or "continue chatting to refine it further." (The /replitai/agent page shows "Accept tasks" / "Revise plan" buttons.)
  - (c) "Agent automatically switches to Build mode" and "begins implementation of approved tasks"; you can "track progress through the development phase." Plan-mode usage is billable.
  - (d) Opt-in ("Plan" button) or by asking for a plan.
  - (e) The July 2025 SaaStr incident (below) is what pushed Replit to add a "planning-only" mode.

- **Amazon Q Developer `/dev`** — https://aws.amazon.com/q/developer/features/ (fetched 2026-08-22; the user-guide page returned no body)
  - (a) "breaks down your prompt into logical implementation steps"; "map out a step-by-step implementation plan spanning multiple files, and upon your approval, run all the required code changes and tests in minutes."
  - (b) Review and iterate: "collaborate with Amazon Q Developer to review and iterate on the implementation, and, when ready, ask Amazon Q Developer to help implement each step." After generation, "Provide feedback & regenerate" (https://aws.amazon.com/blogs/devops/enhancing-code-generation-with-real-time-execution-in-amazon-q-developer/).
  - (c) Approval gates code generation; diffs reviewed and accepted afterwards. (d) Always for `/dev`. (e) None found.

- **Lovable Plan mode (formerly Chat mode)** — https://docs.lovable.dev/features/plan-mode (fetched 2026-08-22)
  - (a) "a dedicated Plan view as a readable, structured document"; "A plan is created only when there is a clear implementation to propose"; Lovable "often asks clarifying questions."
  - (b) "Plans are fully editable before approval."
  - (c) "When you approve a plan, Lovable switches to Build mode" and "implementation begins based strictly on the approved plan." "Plan mode never modifies your code."
  - (d) Opt-in (Plan button). (e) None found. Rename from "Chat mode" was to "better reflect how the mode is intended to be used before implementation" (https://lovable.dev/faq/ai-agent/plan-mode).

- **Bolt.new Plan Mode / Discussion Mode** — https://support.bolt.new/best-practices/discussion-mode (fetched 2026-08-22)

## Group C — pre-AI dry-run and preview lineage

- **`terraform plan` / saved plans** — https://developer.hashicorp.com/terraform/cli/commands/plan and …/apply (fetched 2026-08-22)
  - Preview: plan "proposes a set of change actions that should, if applied, make the remote objects match the configuration." Without `-out`, "it will create a speculative plan, which is a description of the effect of the plan but without any intent to actually apply it."
  - Binding: `-out=FILENAME` writes "an opaque file format that you can later pass to `terraform apply` to execute the planned changes." The file "does contain your full configuration, all of the values associated with planned changes, and all of the plan options including the input variables." On apply: "When you pass a saved plan file to `terraform apply`, Terraform performs the operations in the saved plan without prompting you for confirmation … Terraform interprets the act of passing the plan file as the approval." "When using a saved plan, you cannot specify any additional planning modes or options."
  - What happens if state changed in between: the apply refuses with "Error: Saved plan is stale". HashiCorp staff explanation (https://discuss.hashicorp.com/t/question-on-error-saved-plan-is-stale/52912): state snapshots carry "lineage" and "serial"; "Both of these tracking fields must be exactly equal between the saved plan and the latest state snapshot at the time you run apply." Any intervening apply, another pipeline, or a state edit bumps the serial and invalidates the plan; the fix is to re-plan. Edge cases: data sources that change on every run and backends whose metadata changes can produce stale plans without real change (https://github.com/hashicorp/terraform/issues/27827, https://github.com/gruntwork-io/terragrunt/issues/4170).
  - Residual drift inside a valid plan: "Provider produced inconsistent final plan" is raised when, during apply, the provider's final plan differs from the saved one, e.g. "changed the planned action from Update to DeleteThenCreate" (https://github.com/hashicorp/terraform-provider-aws/issues/33690). So Terraform has two guards: the serial check (the world changed) and the consistency check (the executor would do something other than what was shown).

- **`kubectl --dry-run`** — https://kubernetes.io/docs/reference/kubectl/generated/kubectl_apply/: "Must be 'none', 'server', or 'client'. If client strategy, only print the object that would be sent, without sending it. If server strategy, submit server-side request without persisting the resource." Server dry-run runs admission and validation, so the preview is produced by the same machinery as the real apply. No binding to a later apply.

- **`rsync -n` / `--dry-run`** — https://download.samba.org/pub/rsync/rsync.1: "This makes rsync perform a trial run that doesn't make any changes, and produces mostly the same output as a real run. It is most commonly used in combination with the --verbose (-v) and/or --itemize-changes (-i) options to see what rsync would do." The word "mostly" is the honest caveat. No binding.

- **Ansible `--check --diff`** — https://docs.ansible.com/ansible/latest/playbook_guide/playbooks_checkmode.html: "In check mode, Ansible runs without making any changes on remote systems. Modules that support check mode report the changes they would have made." "Check mode is just a simulation. It will not generate output for tasks that use conditionals based on registered variables (results of prior tasks)." Diff mode: "any module that supports diff mode reports the changes made or, if used with --check, the changes that would have been made." Per-task opt-out: `check_mode: false` forces a task to run for real even under `--check`. Documented limitation of previews that depend on earlier results.

- **Database migration previews**
  - Flyway dry run: "Flyway sets up a read-only connection to the database. It assesses what migrations need to run and generates a single SQL file containing all statements it would have executed" — useful to "submit the SQL statements for review to a DBA before applying them" (https://documentation.red-gate.com/flyway/reference/tutorials/tutorial-dry-runs). Redgate advises regenerating rather than editing the script so "the changes executed match what's in your migrations" (https://www.red-gate.com/hub/product-learning/flyway/dry-runs-for-database-migrations-using-flyway/). The dry-run file can itself be applied by another tool: the preview is the executable.
  - Prisma `migrate diff` outputs "either a summary of the difference or a sql script", which "can be output into a file or be piped to the `db execute --stdin` command" (https://www.prisma.io/docs/orm/prisma-migrate/). Django `sqlmigrate` prints the SQL for a migration without applying it. Rails: no built-in dry run confirmed.

- **IDE refactoring previews** — IntelliJ: "Click Preview in the Refactoring Preview dialog to see potential changes (the list of usages where the refactoring will be performed)"; "In the Find tool window that opens, check the changes that are going to be made"; you can exclude usages; "Click Do Refactor to proceed with the changes" (https://www.jetbrains.com/help/idea/refactoring-source-code.html). VS Code: "In the Refactor Preview panel, you can preview the changes that will be applied by a refactoring operation"; "select any of the changes … to get a diff view"; "Use the Accept or Discard controls"; you can "partially apply the refactoring changes by deselecting some of the proposed changes" (https://code.visualstudio.com/docs/editing/refactoring). Both are per-site editable previews: the actor prunes the list and the pruned list is exactly what executes.

- **Find and replace across files (VS Code)** — "When you type text into the Replace text box, you will see a diff display of the pending changes"; you can "replace across all files from the Replace text box, replace all in one file or replace a single change" (https://code.visualstudio.com/docs/editing/codebasics). Same shape: a diff per hit, prune, then apply.

- **Excel Flash Fill** — Microsoft's own page was not fetchable (404 on the cited URL); third-party documentation is consistent: after a couple of examples Excel "will then show a preview in light grey that you can accept by pressing Enter" (https://www.howtoexcel.org/flash-fill/). The preview is a sample of output rendered in place, accepted by a single keystroke; no plan, no steps.

- **Trifacta / Wrangler** — the original Wrangler paper describes an interface that lets "analysts … iteratively explore the space of applicable operations and preview their effects" (Kandel et al., CHI 2011; cited in https://jrodthoughts.medium.com/technology-friday-trifacta-wrangler-af897bf9a474). Previews run on a sample; the recipe is then applied to the full dataset. A case of preview-on-sample with execution-on-whole.

- **Photoshop / Lightroom batch** — *not confirmed* that either offers a pre-batch preview. Adobe's Batch and Image Processor docs describe options dialogs, not previews; Lightroom Sync Settings shows a checklist of which settings will be copied, not the resulting images (https://helpx.adobe.com/photoshop/desktop/automate-tasks/process-a-batch-of-files/batch-process-files.html). Treat as a "declared scope, no sample" form.

- **Installers** — the macOS Installer "Standard Install" page ("This will take X MB of space on your computer") and Windows MSI "Ready to install" summary are from general knowledge; I could not locate a citable page and mark them *not confirmed*.

- **Scheduled send (Gmail)** — "You can schedule your emails to send at a later time"; "When you cancel a scheduled email, it becomes a draft" (https://support.google.com/mail/answer/9214606). A review window rather than a plan: the composed artefact is held, visible in a "Scheduled" folder, and retractable until the moment of execution.

- **Preview deployments / review apps** — Vercel: "Preview environments allow you to deploy and test changes in a live setting, without affecting your production site"; a preview deployment is created on every non-production push or PR, with a branch URL and a commit URL (https://vercel.com/docs/deployments/environments, updated 2026-07-28). Heroku: "Review apps run the code in any GitHub pull request in a complete, disposable Heroku app … a great way to propose, test, and merge changes" (https://devcenter.heroku.com/articles/github-integration-review-apps). These preview the result rather than the plan, and what is promoted to production is the same build that was reviewed (Vercel "promoting a deployment"), which is the binding.

## Group D — pattern catalogues and published design guidance

- **Shape of AI — Action plan** (https://www.shapeof.ai/patterns/action-plan, fetched 2026-08-22): the AI "lay[s] out its intended steps before it runs, giving users a chance to confirm or adjust." "The right time to stop an erroneous run is before it begins." Two modes: an advisory mode where "AI is trained to use action plans as a tool for reasoning," and contractual modes that "require user verification before proceeding" (examples given: Replit, Devin, Chronicle). Considerations: "A preview reassures users that the system is aligned before it spends compute or makes changes"; "Give them the tools to understand and correct the error then and there"; "Provide shortcuts to hide or minimize the plan, but keep the ability to review available"; on drift: "A plan is only useful if the system follows it. If execution diverges, the plan must be updated or explained." Trade-off: "Confirmations add friction, but they also act as a safeguard in high-risk domains where trust is easily lost."
- **Shape of AI — Sample response** (https://www.shapeof.ai/patterns/sample-response): "Sample responses are lightweight outputs generated before committing to a full, time-intensive result. They give users a quick preview of what the AI intends to do, letting them confirm direction before resources are consumed or content is overwritten." Default to sampling "when risk or blast radius is high"; "Let users skip if they want"; show cost and time before scaling up. Example: Notion's "try on this view" before running across a whole database, warning that it "will overwrite user data." Distinguished from Draft mode (lower-quality outputs for parameter testing). Related Shape of AI entries: Verification ("Allow user confirmation before AI action execution"), Cost estimates, Controls (pause/redirect mid-stream).
- **AI UX Playground — Plan & Execute** (https://www.aiuxplayground.com/pattern/plan-execute): "the agent first breaks a complex goal into an explicit, ordered list of steps, then works through that plan sequentially while showing progress." For "multi-step agent tasks where users benefit from seeing intent before side effects start." Skip for "single-step requests where a plan adds a review step with nothing to actually review." Editing state: "the person adjusts, reorders, or removes steps. Execution will follow the edited plan." "One clear CTA ('Run plan', 'Start') commits to the visible sequence. Do not auto-run without consent." Anti-pattern: "showing a plan once and then silently deviating from it during execution with no updated view."
- **AI UX Playground — Sandbox Preview** (https://www.aiuxplayground.com/pattern/sandbox-preview): "dry-runs a plan (showing intended side effects, diffs, or receipts) before execution." Examples cite Terraform, CI simulation, sample personalised emails before bulk send, coding-agent diffs. Anti-patterns: "Previews that omit irreversible effects present in the real plan"; "Execute buttons that skip sandbox after the first approval forever"; "walls of logs with no human-readable summary of blast radius."
- **AI UX Playground — Blast Radius Visualization** (https://www.aiuxplayground.com/pattern/blast-radius-visualization): "previews how many files, records, users, or systems an action will touch before approval." Use "concrete counts ('412 files across 37 folders')." Skip when "accurate counts require executing the mutation first." Anti-patterns include "Letting counts balloon mid-run without re-confirmation."
- **aiuxdesign.guide — Intent Preview** (https://www.aiuxdesign.guide/patterns/intent-preview): the agent presents "a clear, scannable summary of what it intends to do - showing planned steps, reversibility status, and edit controls for user approval." For actions that are "consequential or hard to reverse: sending mail, moving money, deleting files, booking, posting." Do not preview the "trivial and reversible" because it "trains reflexive approval." Named anti-pattern, the cosmetic preview: "a tidy, reassuring summary that doesn't match what actually executes" which "manufactures consent." Principles: "Render previews from the same plan the executor runs"; "Never auto-run if plans change after approval"; "Record previewed plans alongside executed actions."
- **aiuxdesign.guide — Plan Summary** (https://www.aiuxdesign.guide/patterns/plan-summary): "While Intent Preview shows WHAT the agent will do, Plan Summary explains WHY and HOW": goal interpretation, strategy, "a subtask checklist that updates in real-time, explicit assumptions the user can correct, and resource and time estimates." "Update the plan in real-time during execution. Show completed steps, current step, and remaining steps"; highlight deviations. Suggested metrics: "plan modification rate, plan deviation rate, and assumption correction rate."
- **Microsoft HAX guidelines** (https://www.microsoft.com/en-us/haxtoolkit/library/): G1 "Make clear what the system can do"; G2 "Make clear how well the system can do what it can do"; G9 "Support efficient correction — Make it easy to edit, refine, or recover when the AI system is wrong"; G10 "Scope services when in doubt — Engage in disambiguation or gracefully degrade … when uncertain about a user's goals"; G11 "Make clear why the system did what it did"; G16 "Convey the consequences of user actions." A plan preview is the G1/G16/G9 bundle applied at task scale. The HAX library has no guideline specific to plan approval.
- **Google PAIR guidebook** (https://pair.withgoogle.com/chapter/mental-models/): nothing on plans or previews; the nearest is "Be up-front about what your product can and can't do the first time the user interacts with it." The guidebook predates agents.
- **Apple HIG "Generative AI"** (https://developer.apple.com/design/human-interface-guidelines/generative-ai): page exists but renders client-side; body not fetchable. *Not confirmed* whether it addresses previews or confirmation for agent actions.
- **Anthropic** — the plan-mode docs above, plus the auto-mode engineering post with the 93% figure. **OpenAI** — Operator/agent confirmation text blocked; see Group B. **Microsoft** — Magentic-UI blog (Group B) is the explicit "co-planning" argument.

## Takeaways for the pattern page

- The two things that make a preview binding are rare and both come from Terraform: refuse to execute if the world changed since the plan (serial/lineage "Saved plan is stale") and refuse if the executor's final plan differs from the shown one ("inconsistent final plan"). No agentic tool documents either check; they bind by switching modes and trusting the model. The page can name this gap directly.
- Plans in coding agents are converging on an editable markdown file stored outside the repo (Claude Code `~/.claude/plans`, Cursor home directory, Windsurf `~/.windsurf/plans`, Copilot `/memories/session/plan.md`). The file is the contract; editing it is the correction channel; the same file is re-read by the executor. That is the plan-as-artefact form worth describing, distinct from the plan-as-chat-message form (Jules, Replit, Bolt).
- Live tick-off is what keeps the preview honest during execution. Copilot's PR checklist and Manus's todo.md do it; Claude Code does not. Manus frames the checklist as being for the agent's own attention as much as the actor's, which is a useful argument: the same artefact steers the executor and informs the reviewer.
- Review fatigue is documented with a number (93% approval of permission prompts, Anthropic) and two products have designed around non-response with timers (Jules, Devin). The pattern page should say when not to preview (aiuxdesign.guide: trivial, reversible actions "train reflexive approval"; AI UX Playground: single-step requests "with nothing to actually review").
- Documented drift incidents are mostly scope errors in a correct-looking command (`rm -rf … ~/`, wrong shadow database, wrong partition), not wrong step lists. That favours file-touch and blast-radius forms (counts, targets, irreversibility marks) over prose step lists, and favours previews generated by the same code path that executes (server-side dry run, refactor preview) over summaries written by the model about itself ("cosmetic preview").
- The pre-AI lineage shows a clean split: tools that preview the plan (terraform, ansible, rsync) and tools that preview the result (Flash Fill, Trifacta samples, Vercel previews, Shape of AI Sample response). Both are "plan preview" in the pattern's sense; the page should name the choice and when each fits (result samples when output quality is the risk; action lists when side effects are the risk).
- Partial acceptance is an old, proven correction move: IntelliJ and VS Code refactor previews let the actor exclude individual sites and then execute exactly the remainder. Agent plans mostly offer whole-plan edit or chat feedback; per-step exclusion (AI UX Playground "adjusts, reorders, or removes steps") is worth calling out as the stronger form.
- Cost is a first-class reason for previewing in several products (Bolt's 90% token saving, Shape of AI's "before it spends compute"), not only safety. The pattern's "cost" element has practice behind it.

# Research: platform variance — where it lives in the schema — 2026-08-06

Query: how a pattern language should encode platform and device variance, and
whether input capability is the axis. Run as a falsification exercise against a
stated strawman rather than a search for support.

> *Retrieval provenance*. Five search angles, 21 sources fetched, 102 claims
> extracted, top 25 verified by three-vote adversarial panels. 15 confirmed, 10
> refuted. Primary sources carried the weight: W3C Media Queries Level 5, WCAG
> 2.2 plus its Understanding docs, Material 3 and Android developer docs read
> live, and Wobbrock et al.'s Ability-Based Design (TACCESS 2011) read in full.
> Practitioner sources (LukeW, Cloud Four, Karen McGrane, CSS-Tricks, Smashing)
> supplied the responsive-orthodoxy angle. Two angles came back thin and this is
> load-bearing — see *What this gate does not establish*.

## Context

From `query.yml`: 136 pattern pages, about a dozen carrying ad-hoc device prose,
no schema construct for any of it. The strawman under test held that the real axis is
input *capability* rather than screen size, that "mobile" is a bundle of
correlated capabilities that merely co-occurs with a narrow viewport, and that
the condition belongs on `situation.initiating`.

## What the sources establish

### Shipping systems replaced device class with *window* size, and the argument was dynamism

Android states it flatly: window size classes are "explicitly not determined by
the size of the device screen" and "not intended for isTablet-type logic". The
reason given is that the class is a runtime property — "device orientation
changes, multitasking, and folding/unfolding can change the amount of screen
space available. As a result, the window size class is dynamic." Named
mechanisms: split-screen partitioning, arbitrarily resizable Android windows on
ChromeOS, foldables with two differently-sized screens. Material states the same
as a rule: "Design for breakpoints instead of specific devices."

This defeats the move of dismissing any viewport axis as device class in
disguise. The window is a property of the surface at a moment, not of the
hardware. It does not establish that a window axis is *sufficient*.

### Material subsumes input under width, and the model provably cannot carry the distinction

The breakpoint definition bundles three concerns into one scalar: "the window
size at which a layout needs to change to match available space, device
conventions, and ergonomics." Input appears once, subordinated: "Repositioning
is also a way to match the ergonomic and input needs that change across device
sizes." A keyword scan of the rendered breakpoints page returns *hover* 0,
*pointer* 0, *mouse* 0, *keyboard* 0, *touch* 0, *stylus* 0.

The checkable consequence: Material's Expanded class (840–1199dp) contains
"Phone in landscape", "Tablet in landscape", "Foldable in landscape" and
"Desktop" together. A width key cannot separate a touch-only phone from a
mouse-and-keyboard desktop. Material's sibling adaptive-design page concedes the
point in prose — "designs should be built with all inputs in mind—touch,
pointer, and physical keyboard" — and never operationalises it. Exhortation,
never a branchable condition. Material needed a second construct entirely
("experience type": mobile / desktop / spatial) because breakpoints could not
carry input.

*Sources disagree, do not average*: m3.material.io places Desktop in Expanded
(840–1199dp); developer.android.com pushes Desktop to Extra-large (≥1600dp) and
labels Expanded "97.22% of tablets in landscape". The Expanded-row consequence
above is quoted from the m3 table specifically.

### Material's structural answer is one corpus, sectioned by kind of adaptation, fenced by functional equivalence

Not per-platform corpora, not per-platform pages. A cluster of about nine pages
organised around five numbered questions: which elements to *reveal*, *divide*,
*resize*, *reposition*, or *swap*. A "Common swappable components" table keys
swaps to breakpoint — navigation bar → collapsed rail; bottom sheet → menu;
full-screen dialog → basic dialog.

The fence is the transferable part: "Make sure the interchangeable components
are functionally equivalent... Don't swap a button for a chip." Plus a Don't
card against swapping components that are not functionally equivalent.

Normativity is guideline-grade, and the construct is internally inconsistent —
two tables on the same page disagree ("Simple dialog" vs "Basic dialog"), the
swap table covers three of five breakpoints, and two per-breakpoint pages 404.

### Capability predicates are not booleans

Media Queries Level 5 defines `hover` and `pointer` by convenience and normal
usage, not physical possibility: "Pointing devices that can hover, but for which
doing so is inconvenient and not part of the normal way they are used, also
match [`hover: none`]." `coarse` is defined behaviourally — a device that could
not "reliably pick one of several small adjacent targets at a zoom factor of 1".

Two constraints matter more than the definitions:

- *Accessibility override.* "Even on devices that do support hovering, the UA
  may give a value of `hover: none`", and likewise `pointer: coarse` "to
  indicate that the user has difficulties manipulating the pointing device
  accurately or at all." Hardware accuracy and user ability collapse into one
  value.
- *Unspecified primacy.* The spec "does not define how user agents should decide
  what the 'primary' pointing device is", and UAs "may also decide to
  dynamically change" it. Implementations diverge in practice — Surface Pro and
  Dell XPS have been reported as `pointer: coarse`.

The consequence that joins this to the WCAG finding: because a UA may deny hover
on capable hardware for accessibility reasons, "this move needs a hover channel"
is a dependency the platform will sometimes refuse. That converts it from a
variance question into a floor question.

### Two of the four proposed predicates are not expressible at all

The spec is explicit that the interaction features "can not be used to detect
the presence of non-pointing device input mechanisms such as keyboards. Authors
should take into account the potential presence of non-pointing device inputs,
regardless of which values are matched." Nothing in the feature set addresses
reach, grip, one-handed use, or physical ergonomics. And "it is currently not
possible to provide different styles for cases where different pointing devices
have different hover capabilities."

CSSWG issue #3871, "Detect physical keyboard", has been open since 2019, stalled
on definition and fingerprinting concerns.

*Qualification*: keyboard **use** is observable reactively (`:focus-visible`,
keydown-modality detection). What cannot happen is pre-rendering a
keyboard-conditional affordance before a key is pressed. And absence from CSS
constrains realisability, not vocabulary — a design-time predicate can be valid
and unqueryable.

### WCAG picks capability as the unit and then writes floors, not branches

This is where the strawman had the right source and the wrong shape.

WCAG's abstraction is `single pointer` — "an input modality that only targets a
single point on the page/screen at a time – such as a mouse, single finger on a
touch screen, or stylus". One abstraction over distinct hardware. Then SC 2.5.7:
"All functionality that uses a dragging movement for operation can be achieved
by a single pointer without dragging, unless dragging is essential or the
functionality is determined by the user agent and not modified by the author."

No antecedent clause of any kind. The two carve-outs are essentiality and
user-agent ownership — the second scopes *authorship responsibility*, not
capability. SC 2.5.8's target size is one device-independent threshold (24×24
CSS px) with five exceptions, none of which is a device or capability predicate.
The working group had full device vocabulary in the rationale layer — "trackball,
head pointer, eye-gaze system, or speech-controlled mouse emulator" — and kept
it out of the requirements. The same essentiality / user-agent-control /
equivalence triad recurs across the Input Modalities criteria, so this is
architectural rather than a one-off.

So WCAG is not precedent for capability-selected design variants. It is
precedent for an *unconditional floor*. Note the contrast, not contradiction:
Material *does* split by input where WCAG does not (48dp touch / 44dp pointer).

### The strongest capability precedent puts the predicate on the actor, not the surface

Ability-Based Design (Wobbrock, Kane, Gajos, Harada & Froehlich, TACCESS 3(3),
2011): "the appropriate question when designing accessible technologies is not,
'What disability does a person have?' but rather, 'What can a person do?'" The
category-is-too-coarse argument is explicit — WHO ICF characterisation is
dismissed as producing "outcomes at too high a level for informing user
interface optimizations".

But ability is not person-intrinsic: "ability is not static; it is influenced by
the context in which it is exercised", with an enumerated list — "ambient noise,
distraction, divided attention, body motion, walking vibration, weather... gloves
causing 'fat fingers'... glare, low light or darkness, encumbering baggage,
confined or crowded" spaces. §5.12 Walking User Interfaces is a shipped instance:
targets enlarge when the user starts walking.

This merges the strawman's capability and context axes into one axis with two
sources. And then the paper keeps them apart anyway, for a stated reason:
"Although context ultimately affects performance, we choose to cite context as
its own principle to emphasize the need for proactive sensing and anticipation
of changes in users' performance due to changes in context." The 2018 CACM
restatement actively revised the framework and both survived, separately.

The transferable move is structural: concede that one axis works through
another, keep both named, and justify the redundancy functionally. Not a
term-for-term schema.

## Design implications

- *Order of operations on a pattern page is floor, then variance.* The floor is
  unconditional: the move works with a single pointer, no drag dependency, no
  hover dependency. Only what survives the floor is a variance case.
- *Hover-dependence is a floor failure, not a device case.* The platform can deny
  hover on capable hardware. A page that says "suppressed on touch" is
  describing a provision gap in device clothing.
- *Say window, never device.* The dynamism evidence is what makes this more than
  a wording preference — a single physical device crosses classes mid-session.
- *Functional equivalence is the fence that keeps one corpus.* If the adaptation
  is a genuinely different move rather than an equivalent swap, it is a
  different pattern joined by an edge, not a variant.
- *Name what changes, not what it changes on.* Material's reveal / divide /
  resize / reposition / swap is the vocabulary that survives being read on a
  surface nobody anticipated.
- *Three condition families, phrased as prose.* Surface (compact / medium /
  expanded window). Input (hover channel, pointer precision, single-pointer
  path, keyboard) — only the first two machine-queryable. Situation (divided
  attention, one-handed, glanceable, interruption-prone), phrased as
  ability-in-context rather than as device attributes.

## What this gate does not establish

Two of five angles came back thin, and the recommendation leans on the gaps.

*Design-system comparison is two Google systems, not an industry.* All three
Apple HIG claims were voted down (0-3, 1-2, 0-3), so nothing here is established
about how the HIG encodes platform variance. Fluent, Polaris, Atlassian, Carbon
and Spectrum produced nothing that survived verification. "Every shipping system
converged on window size" means Material and Android, which are the same
lineage.

*The forking post-mortem does not exist in this pool.* Alexander on scale and
context, Tidwell across editions, van Welie, HCI pattern-language context
specification, faceted classification, and the failure literature on
per-platform forking all returned nothing verifiable. So the central structural
bet — that an equivalence fence prevents corpus forking — rests on Material's
current practice and on no historical base rate at all.

*The case against `situation.initiating` is thinner than it reads.* The
convenient supporting claim, that grip posture flips within seconds and so
cannot be a static predicate, was refuted 0-3. What survives is Android's
window-dynamism evidence, which is about the surface rather than the actor. That
is enough to defer a typed field; it is not enough to rule one out.

*Three claims most convenient to the strawman all failed.* That MQ5 makes
capability primitive and device classes derived (0-3); that the spec's smart-TV
example proves a distinct context axis (0-3); that grip posture is transient
(0-3).

## Citation hygiene

- `m3.material.io/foundations/layout/applying-layout/window-size-classes` hard-404s
  to non-browser clients. The live page is `/foundations/layout/breakpoints/overview`,
  and the construct was renamed: "A breakpoint (previously window size class)".
- `developer.android.com/develop/ui/views/layout/canonical-layouts` is the legacy
  Views tree with a stale three-class table. Current is
  `/develop/adaptive-apps/guides/use-window-size-classes` (five width classes plus
  height classes).
- The SC 2.5.7 text lives at `#dragging-movements`, not `#target-size-minimum`.
- m3.material.io is a client-rendered SPA. `curl` returns 404 shells that read as
  refutation. Re-checks need a real browser.
- Material's breakpoint pages were mid-revision when read on 2026-08-06: two of
  five per-breakpoint pages 404, and two tables on one page contradict each other.
- WCAG 2.2 is the operative Recommendation, now ISO/IEC 40500:2025. WCAG 3.0 is a
  Working Draft and adds no capability branching. CSSWG #3871 is open, so the
  keyboard-unqueryable constraint could change.

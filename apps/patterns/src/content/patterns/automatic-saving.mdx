* * *

**People do not want to manage storage, yet software loses work that has not been written to storage. When an interface adds a Save button out of habit, it forces actors to guard against crashes and remember to commit; when it removes the button without replacing what rode on it, the acts of marking a version, discarding an attempt, and deciding work is ready for others vanish with it.**

Because software storage historically had a button, unrelated human acts gathered onto the same control: declaring that a version counts, discarding an attempt since the last commit, or signalling that work is ready for others. Automatic storage is the right default for open-ended work because lost work cannot be recovered afterwards, whereas each of those acts can be given its own home.

Only a real technical constraint (rate-limited or whole-record writes) or a transaction boundary overrides this default, in which case [pending changes](/patterns/pending-changes) applies instead; a Save button kept only out of habit can go.

Therefore,

**Write changes to storage automatically as the actor works—after a short pause, on a timer, or when focus leaves a field—and give versioning, recovery, and publishing their own controls rather than collapsing them onto a Save button. Report quietly what was stored and when, and interrupt clearly whenever a write fails.**

Do not mix automatic saving with manual save buttons silently across adjacent screens: an actor who sees a Save button on one screen will wonder whether edits on the next screen were kept, so mark which rule applies whenever both must coexist. Silent automatic saving that fails is worse than asking the actor to save.

## In practice

- *Status and failure:* an indicator with a timestamp outlasts a spinner; when a write fails, interrupt clearly and keep a way to retry or copy the unsaved text rather than dropping it.
- *Write timing:* flush fast enough that a closed tab loses nothing, and coarsely enough not to flood storage writes or version snapshots.

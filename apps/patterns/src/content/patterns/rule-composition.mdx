The system does some things by rule while the actor is away: moves files, hides messages, skips songs, stops making certain suggestions. Rule composition is how the actor writes or changes one of those rules. It starts once the actor has decided what should change and has the rule in front of them. The rule is shown as one sentence in plain language, and the actor edits it in place.

> **When** an email arrives **and** it contains the phrase *"Canadian Pharmacy"* **and** it is not
> from *someone in my contacts*, label it *"likely spam"* and move it to *the trash*.

The same control works for a mail rule, a playlist, a thermostat schedule, or an agent's trigger.
What differs between them is the set of parts on offer, not the surface.


## Forces

- *Reading vs. structure* — a rule needs and, or and not, but a sentence reads in one line. Flat
  lists of conditions read fine. Nested groups do not, and grouping is where people make mistakes.
- *Exactness vs. the actor's words* — the rule has to use fields the system has, and the actor's
  reason for wanting it usually does not map onto them.
- *One rule vs. the list* — a rule is written on its own but runs alongside the others. People hold
  specific wrong beliefs about how rules combine: that two rules with opposite actions cancel out,
  that rules run in the order listed, that a condition on one rule limits the others.

## Solution

Show the whole rule as one plain sentence, with the trigger and the action together. Splitting them
hides what the rule does. Then let the actor edit the sentence in place.

When a rule needs grouping that one line cannot hold, break the sentence into lines, one per group,
indented, with the connective between lines. A tree of conditions or a row of chips can show the
same thing, but reads worse for the common flat case, and most cases are flat.

## Events and states

- *Trigger* — something that happens at a moment. "When a file is added to the folder."
- *Condition* — something that is true for a while. "While the project is archived."
- *Action* — what the system does when the trigger fires and the conditions hold.

> People confuse events with states, and the interface causes much of it: "if this, then that" uses the same wording for a moment and for a period. A sentence can keep the two apart with different words: "when" for the event, "while" or "and it is" for the state, then the action. Giving the two kinds of clause different words is an interface fix for what looks like a comprehension problem.

## Showing the effect before saving

The sentence does not say what it will do, so it would be best to show it:

- *Replay the past.* Apply the changed rule to what already happened and show what would have come
  out differently. This is the form that has been shown to improve people's success. It works
  because the cases are real and the actor already has opinions about them.
- *Run it against the other rules.* Step the new rule through alongside the rules already in place,
  so conflicts and loops show up before saving. This is the only form that addresses the
  one-rule-vs.-the-list force.
- *Show the edge cases.* Show the cases that now match for the first time, the cases that match but
  only just, and the cases that miss but only just. A random sample will not include the cases
  that decide whether the rule is right: a country-music rule previewed against a library that is
  mostly not country shows no country at all. This is the form to use when there is no history to
  replay.

>When the rule applies to a visible collection, the preview and the editing become one thing: a [filter](/patterns/filtering) whose result count updates as each condition is added is a preview that runs all the time.

## Research on this pattern

- [Most rules people want are one trigger and one action](https://dl.acm.org/doi/10.1145/2556288.2557420),
  and [shared rules are copied freely](https://par.nsf.gov/biblio/10026427) — the basis for the
  flat sentence and for starting from a draft rather than an empty statement.
- [Grouping is where composition fails, not operators](https://asistdl.onlinelibrary.wiley.com/doi/10.1002/(SICI)1097-4571(199307)44:6%3C327::AID-ASI3%3E3.0.CO;2-J):
  on the same tasks a graphical query builder produced two ordering errors against fifty
  parenthesis errors in SQL.
- [People confuse events with states, and the wording of "if this, then that" causes it](https://dl.acm.org/doi/10.1145/2750858.2805830);
  seven years later the confusion [appeared in 21 of 50 unaided debugging sessions, and every one
  of them failed](https://dl.acm.org/doi/10.1145/3569506).
- [A bug makes a rule harder to predict](https://dl.acm.org/doi/10.1145/3290605.3300782): shown
  rules with one of ten kinds of bug, people got worse at predicting the rule's behaviour for most
  kinds.
- [People hold wrong beliefs about how rules combine](https://dl.acm.org/doi/10.1145/3569506) —
  opposite actions cancelling, rules running in listed order — and
  [replaying the changed rule against past cases was the repair that raised success](https://dl.acm.org/doi/10.1145/3569506).
  [Simulating a rule against the whole standing set](https://dl.acm.org/doi/10.1145/3290605.3300618)
  is the one tested form that reaches conflicts between rules.
- [Offered the system's correct fix among alternatives, only half to three-fifths of people chose it](https://dl.acm.org/doi/10.1145/3569506).
- Untested: the edge-case preview, and whether the sentence form beats a chip row or a tree on the
  common flat case.

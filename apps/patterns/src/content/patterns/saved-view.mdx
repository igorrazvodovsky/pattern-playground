* * *

**When a collection answers recurring questions—my open tasks, urgent customer messages, high-priority bugs—rebuilding the same filter, sort, and column setup on every visit turns routine work into repetitive setup. Yet filing items manually into static folders forces actors to maintain membership by hand and breaks the moment an item belongs in two places at once.**

### Forces

- *Live membership vs. sudden disappearance*: items enter and leave automatically as properties change, yet editing an item in place so it stops matching (reassigning a task inside "My tasks") makes it vanish mid-thought unless the view buffers or signals the exit.
- *Personal vs. shared authorship*: saved views span three authorship poles—shipped defaults, shared role/team views, and private personal views—so exploratory tweaks on a shared view risk silently altering what colleagues see.
- *Accumulation vs. staleness*: saved views are cheap to create and pile up in navigation; when a referenced field, tag, or status label is renamed or retired, the query goes stale silently unless flagged.
- *Write-through ambiguity*: creating or dropping an item inside a saved view requires deciding whether the system stamps the matching properties (`assigned = me`) automatically or refuses the write.

Unlike [bookmarking](/patterns/bookmarking) (which points to a static item) or [remembered state](/patterns/remembered-state) (which silently restores only the last view), a saved view is an explicit, named rule and presentation that updates live. Expressed as a declarative specification decoupled from its data source, it can also travel across collections as a portable personal lens (Min & Xia, 2025).

Therefore,

**Let the actor save any collection framing—its query, representation, arrangement, and visible attributes—as a named, live view reachable from navigation. Keep its defining criteria inspectable and editable, mark views whose referenced fields or values have gone stale, separate personal edits from changes to shared views, and provide a lightweight way to prune views that are no longer used.**

Treat adjustments on a shared view as unsaved local changes until the actor explicitly chooses to update the view for everyone or save a personal copy. When an in-place edit causes an item to leave the current view, keep it visible briefly or offer an undo so the exit does not read as data loss.

## In practice

### Creating or dropping items inside a saved view

When the saved view's rule is a simple conjunction of equality conditions (`type = task` and `assigned = me`), creating a new item inside the view can pre-fill those fields automatically—with the applied values shown transparently. When the rule involves negation, ranges, or computed fields (`total_cost < 250`), pre-filling is ambiguous and the view should either prompt for the missing fields or explain why the new item may not appear there.

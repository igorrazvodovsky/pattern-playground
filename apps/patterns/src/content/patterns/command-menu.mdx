**When an interface exposes every capability in persistent toolbars and nested menus, the surface crowds and actors spend their attention hunting through someone else's hierarchy; when it hides capabilities behind keyboard shortcuts, only actors who have memorised the bindings can reach them. Invoking commands by name cuts through the hierarchy, but shifts the work from recognition to recall: actors often do not know what the system calls the action they want, and an unprompted text box hides what the surface can do.**

Most actors remain perpetual intermediates ([mastery](/patterns/mastery)): they use a tool daily and know what they want to do, yet never memorise a full set of [keyboard shortcuts](/patterns/keyboard-shortcuts) ([Cockburn et al., 2014](https://doi.org/10.1145/2659796)). A command menu sits between visual menu scanning and memorised key bindings. The actor only has to recall a fragment of a name—a verb, an object, or a few initials—and incremental filtering turns the rest of the act back into recognition over a short ranked list. Because each entry displays its keyboard shortcut beside the label, every lookup also rehearses the faster path at the moment of intent ([Malacria et al., 2013](https://doi.org/10.1145/2470654.2470735)).

Two failure modes limit the pattern. First, naming requires a shared vocabulary: two people naming the same operation spontaneously choose the same word less than 20% of the time ([Furnas et al., 1987](https://doi.org/10.1145/32206.32212)), and actors often query by the effect they want rather than the feature's name ([Fourney et al., 2011](https://doi.org/10.1145/2047196.2047224)). A menu that matches only exact labels is fast for actors who already speak the tool's language and no help to actors who came looking for it. Second, because the menu shows only what applies in the current context, inapplicable commands are absent rather than visibly out of reach—which clears away irrelevant clutter, but turns a command the actor expected to find into a mystery unless [unavailable actions](/patterns/unavailable-actions) are accounted for.

Across tools, the pattern appears at two scales:

- *Global command palette*: summoned from anywhere by a shortcut (such as `⌘K` or `⌘⇧P`) or a header trigger as a transient overlay over the [workspace](/patterns/workspace). It spans application-wide actions, navigation jumps across sections, settings, and [recent items](/patterns/recents).
- *Local inline menu*: summoned where a capability has a command space of its own, such as inside a text field, composer, or [block-based editor](/patterns/block-based-editor), by typing a trigger character (usually a slash). It opens at the caret, the actor names the action first, and what the action applies to follows from where the caret is. Nothing has to be selected beforehand, which is the difference from [contextual actions](/patterns/contextual-actions).

What holds constant across both scales is that a transient text input filters a ranked list of executable commands in place, matches fragments and aliases rather than exact prefixes alone, shows the shortcut or trigger beside each entry, and closes cleanly to return focus to the work as soon as the command runs or the actor cancels.

Therefore,

**Give the actor a keyboard-summoned input—opened globally from anywhere in the workspace or locally by a trigger character at the caret—that filters the available actions and destinations as they type and executes the chosen entry on commit. Before a query is typed, open with recent and bookmarked items; as the actor types, match across command names, synonyms, and initials, rank context-relevant and recently used commands first, and show each command's keyboard shortcut or trigger beside its label.**

Do not use a command menu to justify stripping everyday actions from the visible surface: actors who do not yet know what the tool can do cannot guess its names, so the main workflow must stay operable without opening the menu. In an inline slash menu, treat the trigger character as ordinary text whenever the actor keeps typing past the last match or presses Escape, so writing a literal slash in prose never traps the cursor.

## In practice

### Parameter drill-in and action–object order

Many commands need both an operation and a target (*Move issue to… → Backlog*, *Change status… → In progress*, *Insert block → Heading 2*). A command menu handles multi-part commands by drilling into a secondary list inside the same input: choosing the parent command pins it as a scope token in the input and swaps the list to its valid arguments, with Backspace or Escape stepping back one level. Supporting both orders—picking the action first (*Assign to… → Alice*) and picking the object first (*Alice → Assign*)—lets the actor start with whichever part is top of mind.

### Prefix modes in unified launchers

When one input combines command execution with content [searching](/patterns/searching), [workspace](/patterns/workspace) switching, or [prompting](/patterns/prompt), lightweight mode prefixes keep the lists from colliding: typing `>` scopes the bar to commands, `@` to people or references, `#` to tags or issues, and `/` inside a composer to inline commands. Render the active scope as a removable chip in the input so the mode stays visible and escapable ([modality](/patterns/modality)).

### Vocabulary aliases and fallback

Because actors type the words they know rather than the label in the menu, index each command with common synonyms, task verbs, and category names alongside its display title, and support subsequence or initial matching (`gi` for *Go to inbox*). When a query returns no lexical match, offer a way on rather than stranding the actor on an empty list: an [agent fallback](/patterns/agent-fallback) that finds the command by meaning, or handing the query to [search](/patterns/searching) or a [prompt](/patterns/prompt).

## Research on this pattern

- *Vocabulary mismatch in command naming*: [Furnas, Landauer, Gomez and Dumais (1987)](https://doi.org/10.1145/32206.32212) found that two people naming the same command or object spontaneously chose the same term less than 20% of the time, and a single designer-chosen name matched an untutored actor's first try only 7–18% of the time. Indexing multiple aliases gathered from use did far better than any single label.
- *Bridging goal descriptions to feature names*: [Fourney, Mann and Terry (2011)](https://doi.org/10.1145/2047196.2047224) (*Query-Feature Graphs*) and [Adar, Dontcheva and Laput (2014)](https://doi.org/10.1145/2642918.2647395) (*CommandSpace*) showed that actors often search by desired outcomes ("black and white") rather than system command names ("desaturate"), and that mapping natural-language task phrases onto command vocabularies bridges that execution gap.
- *From menu scanning to shortcut adoption*: [Cockburn, Gutwin, Scarr and Malacria (2014)](https://doi.org/10.1145/2659796) reviewed why actors remain in visual menu navigation even when faster accelerators exist, and [Malacria, Bailly, Harrison, Cockburn and Gutwin (2013)](https://doi.org/10.1145/2470654.2470735) showed that exposing hotkey bindings during active command selection promotes shortcut rehearsal and adoption in the flow of work.
- *Named commands beside open prompts*: [Lehmann and Buschek (2024)](https://arxiv.org/abs/2410.10644) observed that repeated prompts for the same operation compress toward one- or two-word commands, with actors relying on named commands and controls for predictable, recurring operations and open prompts for novel combinations.

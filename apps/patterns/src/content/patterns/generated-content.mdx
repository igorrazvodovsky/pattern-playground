* * *

**Generated content is cheap, varies from one draw to the next, and follows from what was asked. Used according to its nature, it is neither a record to rely on as it stands nor scrap to discard once read. It is one of the answers a request allows, good for the situation it was asked in, and it can be asked for again.**

Each property gives the actor something written content does not. Because the output follows from the request and its context, it can be changed by saying what is wanted, without doing the work by hand. Because each draw differs, the one in hand is not the only answer, and asking again is a real option. Because a draw costs little, an actor can start before knowing what they want.

Both ways of mistaking it lose this. Treated as a record, the output is relied on in details nobody chose, repaired by hand when changing the request would have been quicker, and protected from a redraw that would have improved it. Treated as scrap, a good result is gone when the next one arrives, and nothing shows what produced it.

How much infrastructure this requires depends on where the output lands. A single reply in a chat thread needs very little because the thread already preserves the prompt and sequence of turns. A generated draft being inserted into a document, a set of edits to existing files, or a generated interface the actor plans to reuse can easily fail in either direction.

Therefore,

**Wherever generated output appears, treat it as an answer that holds for now and can be asked for again. Keep the request and context beside the result, so that changing them is the ordinary way to change it. Leave asking again open. Keep draws without the actor having to ask, and keep whatever a new draw replaces within reach, whether an earlier draw or content someone has since changed.**

## In practice

How these mechanics appear depends on the surface where the generated output lands.

### A reply in a conversation

In a conversation thread, the preceding message is the request and the thread history automatically preserves both the prompt and the response. What the interface still needs to provide is version handling on the reply itself: a control to regenerate the response, a way to edit and re-run the prompt, and a switcher to step back through earlier replies.

### A view derived from a source

A summary above search results or an overview of a long document is recomputed on demand and is not meant to be stored as content. Here, the priority is linking claims in the summary back to the source passages they came from. If the actor wants to keep a particular version before the view refreshes on their next visit, they need an action to copy, pin, or extract it into a saved note.

### A draft joining a document

When an agent drafts text for an existing document, hold the draft in a staging state until the actor chooses what to do with it: insert it (in full or in part), regenerate, refine the request, or dismiss it. Once the draft is inserted into the document, it becomes the actor's own text; generating again after they have made manual edits should create a fresh candidate or a reversible change rather than overwriting their edits.

### Changes to existing content

Here the output is a set of proposed edits. The interface can stage them as a diff for the actor to review, or apply them directly as a coding agent does when working autonomously. In both cases, keep each set of edits linked to the request that triggered it so the actor can judge whether the changes match their intent. Applying edits without up-front review requires a reliable history of what each change replaced so the actor can inspect or revert it afterwards.

### A generated interface

When the agent generates UI controls or layouts rather than prose, the actor can ask for a different layout just as easily as a different paragraph. However, regenerating an interface also moves controls the actor has already learned to use. If the actor intends to return to a generated view, give them a way to lock, name, and reopen that specific version unchanged.

## Research on this pattern

- Comparing multiple outputs reveals information that a single output hides. Shown agreement and disagreement across samples of the same response, [participants used the number of supporting samples as their main cue for which claims to trust](https://doi.org/10.1145/3613904.3641904). Design principles drawn from generative applications [name variability between outputs and imperfection of any one output as properties to design for](https://arxiv.org/abs/2401.14484), not defects to hide. Holding several versions of a passage in place, [without one overwriting another, lowered workload in revision](https://doi.org/10.1145/3613904.3641899).
- Polished formatting discourages verification. Confident tone and clean formatting lead actors to [treat an early draft as authoritative, and checking it means rebuilding its structure by hand](https://www.nngroup.com/articles/ai-chatbots-discourage-error-checking/).
- The connection to the original request weakens over a long exchange. In data analysis with a conversational assistant, participants [lost track of the assumptions that had accumulated across long responses; breaking the work into editable steps made correcting and verifying easier](https://arxiv.org/abs/2407.02651).
- Accepting generated text is not the same as feeling ownership over it. People [do not regard generated text as their own, yet present it under their name](https://doi.org/10.1145/3637875).

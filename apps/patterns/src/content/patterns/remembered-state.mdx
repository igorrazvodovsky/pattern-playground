* * *

**When an interface resets to its default state on every visit, the actor has to repeat the same setup work each time: re-applying filters and sort orders, reopening tabs, resizing panels, re-selecting the last folder, or scrolling back to where they stopped reading. Each adjustment is small, but the repetition adds friction to every return.**

Persisting state works when the system distinguishes intentional configuration from transient interaction. View arrangements ([sorting](/patterns/sorting), [filtering](/patterns/filtering), grouping, selected tabs, panel widths), reading or playback positions, and last-used picker values are worth keeping; transient states such as focus, hover, open menus, or validation errors are not. Time and content stability also constrain restoration: returning to a scroll position works when the actor comes back soon to static content, but jumping halfway down a page after weeks away—or after the underlying list has changed—is disorienting.

The main risk of remembered state is invisible persistence. Restored state that is immediately self-evident, such as an open tab or a sidebar width, explains itself. State that alters the dataset without obvious cues—such as a filter left active from last week—outlives the task it was set for and makes excluded items look missing. Scope creates a second tension: storing state locally on the device suits screen-dependent adjustments like panel widths, but fails when the actor expects their view configuration across devices, and exposes one person's activity to the next on shared devices.

Therefore,

**Persist the view configurations, reading positions, and option values the actor explicitly chooses, and restore them automatically on return. Scope layout and viewport adjustments to the device, and scope personal view arrangements to the actor's account so they travel across devices and stay isolated on shared ones. Whenever a [deep link](/patterns/deep-linking) specifies state in the URL, let the URL override stored state. Keep any restored state that narrows or reorders content clearly visible on the surface, with a direct control beside it to reset to defaults.**

Keep persistence rules predictable enough that actors can form a reliable mental model, such as persisting configuration per view. When an interface remembers an inconsistent mix of states, actors cannot tell which adjustments will survive a reload and stop relying on persistence altogether. Where actors need to keep and switch between multiple configurations rather than just the last one they used, give them named [saved views](/patterns/data-view#saved-views).

## In practice

- *View configuration.* Persists sort order, active [filters](/patterns/filtering), grouping, selected representation, visible columns, density, open tabs, collapsed sections, and panel widths. Restore silently on return, keep active filters and non-default sort orders visually prominent, and place a reset action ("Clear filters", "Reset layout") directly beside the affected controls rather than burying it in [settings](/patterns/settings).
- *Reading or playback position.* Tracks scroll offset, the last-open document, or the timestamp reached in audio and video. Restore silently when the actor returns soon—such as navigating back from a detail page to a list—and the content has not changed. After a long absence or when the underlying content has updated, keep the view at the top and offer a way to jump to the previous position, such as an unread marker or a "Resume where you left off" prompt.
- *Last-used values.* Remembers the last folder selected in a file picker, the last export format, or the last delivery option, and pre-selects it as a [good default](/patterns/good-defaults) next time the actor opens the control. Never persist sensitive inputs or destructive choices as defaults.

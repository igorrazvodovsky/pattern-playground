# World re-grounding: individuals, values, actions, facts

Restructure the mock world so its authoritative form is the four-part ontology
the action log already uses, instead of composite entity objects. Today the
entity files (`shared/data/users.json`, `tasks.json`, `documents.json`, …)
conflate an individual's identity with the facts about it — the object shape
carries both. After this plan, identity, state, and history are held
separately, and the entity shapes the rest of the repo consumes are derived
views.

The first slice of this adoption already landed: `shared/data/actions.json`
with typed action records (`action-types.ts`), rendered by demos through
`describeAction`. This plan makes that vocabulary authoritative rather than
supplementary.

## Research checkpoint

This plan commits to a storage convention and invents vocabulary, so it takes
the research gate — after this strawman, before implementation. Framed as
"what would I be wrong about?":

- *Deriving state from a log.* Event-sourcing practice has a decade of scars:
  snapshotting, schema evolution of old events, replay cost, the tension
  between events-as-facts and events-as-intents. Which of those scars apply at
  mock-data scale, and which are noise here?
- *Facts as triples.* Triple/EAV stores (RDF, Datomic-style) have settled
  answers for cardinality, retraction, and reified statements. Does a flat
  `{relation, subject, object}` shape hold up, or does it need cardinality
  declarations per relation?
- *Where rich content lives.* Document bodies and product specifications as
  large structured values inside facts — is there precedent for mixing
  fine-grained relations with blob-valued attributes in one store, and what
  goes wrong?
- *Reactions without a concept partition.* Declarative when/then rules over a
  flat action vocabulary — do rule systems at this granularity stay legible
  without a grouping mechanism, or does the partition turn out to be
  structural rather than organisational?

Findings land in `research/world-regrounding/`; surprises get folded back into
this plan before territory 1 starts.

Run 2026-08-15 (`research/world-regrounding/2026-08-15.md`): the strawman
survived with three corrections, applied below — the concepts deferral is a
divergence from the source model, not a subset (position 8); cardinality and
retraction must be declared per relation and enforced by replay (position 9);
replay verifies declared effects against action-type rules rather than
trusting either (position 10). Log-as-truth with state as deterministic
projection is settled practice across three independent lines; its one
recurring scar, event-vocabulary evolution, collapses at this scale to
copy-and-transform — rewrite the committed history by hand, verify by replay.
Lineage awaits an S2 refresh.

## Target shape

A new `shared/world/` directory becomes the authoritative substrate:

- `relations.json` — a registry of relations with signatures
  (`assignee(Task, User)`, `status(Task, StatusValue)`, `author(Document,
  User)` …) and cardinality; `action-types.json` — a registry of action types
  with the relations each may add and remove. What counts as an individual, a
  value, an action, a fact is settled in
  [docs/specs/world-ontology.md](../../docs/specs/world-ontology.md), grounded
  in `references/Making software meaningful.md`.
- `individuals.json` — bare identities: `{id, kind}` and nothing else. Kinds:
  user, project, task, document, comment, quote, material, component, product,
  service, and `item` for a tracked physical unit (territory 4). Names, roles,
  emails are facts, not attributes.
- `actions.json` — the full history, source of truth. Every individual's
  existence and every current fact is attributable to an action; the world
  starts empty, so no initial conditions exist (creation actions are authored
  for the whole cast and catalogue). Hand-authored, per the standing rule that
  idiosyncratic content is migrated by hand and scripts only verify.
- `facts.json` — *generated by replay*, committed, marked "generated — do not
  edit". A script replays `actions.json` from the empty world and writes the
  resulting fact set. The check that regenerating produces what is committed
  joins the lint gate, alongside the existing staleness checks.
- `rules.json` — declarative reactions: when an action of type X occurs where
  some facts hold, an action of type Y follows. Log entries caused by a rule
  carry `causedBy` (the triggering action or actions — a list, since a rule
  may match several actions at once) and `viaRule` (the rule id), so
  provenance is labelled, not just linked. One rule firing may yield several
  caused actions (set-mapped effects such as cascades), each citing the same
  rule. Causal scopes are derived, not stored: a chain is whatever is
  reachable through cause edges from a root action (one with no `causedBy`).
  A failed action is an ordinary record whose output is an error value — no
  separate failure machinery. (All four points: research note addendum,
  full read of the Onward! '25 paper.)

`shared/data/` stays the consumption layer with its API unchanged: `users`,
`tasks`, `documents`, `getUserById`, bindings, finders — all 66 importing
files keep working. The entity collections are assembled at module load from
`shared/world/` (facts grouped by subject, shaped into the existing
interfaces). Derived attributes that are redundant with facts —
`searchableText` — are computed during assembly, not stored.

## Strawman positions

Decisions taken from internal reasoning; each is open to reversal at the
research gate or by owner verdict.

1. *The log is authoritative; facts are a committed derivation.* One source of
   truth. The alternative (authoritative `facts.json`, log as recent history)
   keeps two authored artifacts that can disagree.
2. *Individuals are `{id, kind}` only.* Every property is a fact. The kind is
   not a fact because it is what the id refers to, not something that happened
   to it.
3. *Values are inline.* A value has no identity and is interpreted by its
   structure — so document rich content and product specification objects
   appear inline as fact objects, not in a separate value store. Large, but
   the current JSONs are already this large.
4. *Statuses, priorities, labels are values, not individuals.* `"executing"`
   is interpreted by content. Their display metadata (colour, label text) is
   UI configuration and stays in `shared/data`, outside the world.
5. *Transactions and lifecycle events are actions, not individuals.* They are
   records of occurrences; they migrate into `actions.json` as typed actions
   of the physical and financial world, and their JSON files retire.
6. *Comments are individuals* (they persist, are referenced, have state), but
   their creation is an action and their text is a value carried by both the
   action input and a fact.
7. *Views must prove equivalence before cutover.* During migration a script
   deep-compares each assembled view against the retired entity file; the old
   JSON is deleted only after the comparison passes. Intentional divergences
   (dropped redundancy, fixed inconsistencies) are listed in this plan's log,
   not silently absorbed.
8. *The concepts deferral is a divergence, not a subset.* In the source model
   synchronizations are defined over the actions of independently defined
   concepts, and state is owned per concept — the partition is structural for
   executable systems (research note, "What this challenges" 1). The flat
   vocabulary holds here because this world is data with no control flow.
9. *Cardinality and retraction are declared and enforced.* Each relation in
   the registry declares cardinality; on replay, single-valued
   relations replace on assertion, many-valued relations accumulate, and any
   other removal must be an explicit `removes` — otherwise facts silently
   pile up (research note, EAV cluster; corroborated by shipped practice in
   the practice note).
10. *Replay verifies effects against action-type rules.* Each action record
    carries both intent (name + input) and effect (`adds`/`removes`); the
    replay script checks the declared effects against the action type's
    required/ensured facts instead of trusting either alone, dissolving the
    events-as-intents vs events-as-facts tension (research note, "What this
    challenges" 3).

## Deliberately not adopted

Recorded per the drafting rule that surviving differences are choices:

- *Concepts.* Owner decision: individuals, values, actions, and facts only.
  Action names stay flat and un-namespaced; `rules.json` reactions reference
  action types directly rather than concept actions. This is a divergence
  from the source model, where the partition is structural (strawman position
  8, research note 2026-08-15). Revisit trigger: any move toward an
  executable world — demos firing actions through a runtime, or an agent
  operating the world — at which point concepts stop being optional; a
  secondary trigger is the action vocabulary growing past easy legibility.
- *A runtime precondition engine.* Action signatures declare required facts in
  the registries, and the replay script enforces them during generation, but no
  runtime machinery checks preconditions when demos fire simulated actions.
  The world is data, not an executable system.

## Territories

Migration-shaped work, segmented by territory, each closed in one sitting
against its definition of done. Reflective verdicts (ontology decisions,
relation naming) first and unhurried; mechanical extraction batched.

1. *Substrate and workspace domain.* `shared/world/` scaffolding, the
   registries, replay + equivalence scripts. Users, projects, tasks migrated:
   creation and lifecycle actions authored (folding in the existing
   `history[]` arrays), facts generated, views assembled, `users.json` /
   `projects.json` / `tasks.json` retired. Done when: equivalence passes,
   lint gate includes replay staleness, task `history[]` is gone as a private
   event shape.
2. *Documents, comments, quotes.* Authorship, threading, anchoring as
   relations; rich content as values; the existing comment/quote timestamps
   become creation actions. Done when: commenting services and editor demos
   run on assembled views, `comments.json` / `quotes.json` / `documents.json`
   retired.
3. *Circular-economy catalogue.* Materials, components, products, services;
   composition relations (`material-of`, `component-of`) replace nested
   id-arrays in metadata. Deep product metadata stays a value. Done when:
   traversal finders (`getMaterialsUsedInProduct` …) read facts, catalogue
   JSONs retired.
4. *Occurrences.* Transactions and lifecycle events re-authored as actions;
   the two JSONs retire; `Table` and `semantic-zoom` consumers read from the
   log through the existing view shapes. Done when: no `.json` under
   `shared/data/` describes a happening.
5. *Rules and provenance surfacing.* `rules.json` authored for the reactions
   the log already implies (notify on comment, notify on completion, status
   automation); `viaRule` added; the activity-log demo surfaces the labelled
   provenance. The strawman also named action-consequences and notification
   here; reading them showed neither renders a log entry at all — one is a
   confirmation-friction ladder, the other a single delete dialog — so neither
   is a provenance surface. Done when: every `causedBy` in the log cites a rule
   that licenses it, and replay checks the reverse as well.
6. *Residue.* Spec deltas applied (below), `shared/data` bindings and types
   reconciled (the half-done `task-types.ts` consolidation closes here),
   tech-debt entries for anything discovered but out of scope.
